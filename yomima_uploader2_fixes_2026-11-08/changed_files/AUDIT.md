## 第1部 まず結論（新規発見のうち重要なもの）

段階に分けて、影響の大きい順に並べます。詳しくは第3部を見てください。

1. **いま新規インストールすると、登録・ログイン自体が壊れます**（N-1）。`requirements.txt` に版指定のない passlib と、その相方 bcrypt の現在版（5.0.0）の組み合わせで、パスワードのハッシュ化が例外を投げます。実際に venv を作って確認しました。

## 第3部 新規発見（メモに無いもの）

深刻度の目安: 高＝外から悪用できる／機能が丸ごと壊れる、中＝条件付きで壊れる・情報が漏れる・記録が狂う、低＝限定的・将来の事故の芽。

### N-1新規インストールでは認証が壊れている（依存ライブラリの版が無指定）

- 場所: `mangaupload_yomima_site/requirements.txt:9-14`（`passlib`、`httpx`、`python-jose`、`sqlalchemy`、`slowapi`、`email_validator` に版指定なし。bcrypt は passlib の依存として間接的に入る）
- 何が起きるか: 2026-11-08 時点の最新版で venv を作ると bcrypt 5.0.0 + passlib 1.7.4 になり、`main.py:300` の `pwd_context.hash()` が**どんなパスワードでも** `ValueError` を投げ、登録APIが 500 になります（R-1 で実測）。passlib 側が内部テストで72バイト超のパスワードを使い、bcrypt 5 が「切り捨て」を例外に変えたためです。つまり「新しく環境を作った人ほどログイン機能が最初から動かない」状態です。
- 修正案: `bcrypt==4.0.1` のように動く組み合わせへ固定する、または passlib を外して bcrypt / argon2 ライブラリを直接使う。あわせて全依存に版の上限・下限を付け、登録→ログインの最小テストを用意する。

### N-2メモ「丁：要確認」は確定 ― 保存型 XSS の経路が複数ある

メモの丁は「`esc()` はあるが素通しの箇所がある。自分のファイル名なら影響は自分だけかも」という留保でした。今回、入力の出どころまで追った結果、**他人の入力が他人のブラウザで実行される経路が確定**しました。段階に分けます。

1. **土台**: 作者画面の `esc()`（`static/index.html` 末尾）は HTML の文字実体化しか
しません。「`onclick="関数('${esc(値)}')"`」のような **JavaScript 文字列の中**に値を埋めると、ブラウザは属性値を読む段階で `&#39;` を `'` に戻してから JS として解釈するため、値に `'` を含めるだけで文字列を抜け出せます。これは `esc()` の設計ミスではなく「使う場所（文脈）に合った逃がし方をしていない」問題です。
2. **一番重い経路（クリック不要）**: 作者画面のジャンルフィルタ生成 `buildGenreFilterButtons()`（`static/index.html:476-482`）は、タグ文字列 `g` を**無加工で** `innerHTML` にも `onclick` 属性にも埋めます。タグの出どころはカタログAPIの `genre_tags` で、その元は作者が設定保存で送った文字列そのものです。後サーバー側の DB 同期は固定表にあるタグしか拾いませんが、**`settings.json` には送られた文字列がそのまま保存され、カタログはそちらを返す**（`main.py` の `update_settings` と `public_catalog`）ため、APIを直接叩ける作者は表に無い任意の文字列を `genre_tags` に入れられます。`<img src=x onerror=...>` のような文字列を入れれば、カタログを開いた**全訪問者のブラウザで、ボタンを描いた瞬間に**スクリプトが動きます。
3. **クリックで発火する経路（公開側）**: カタログ描画のモチーフタグ（自由入力）のチップも `onclick="clickCatalogTag('${esc(t)}')"` の形で、上記1の理由で `'` を含むタグをクリックした訪問者のブラウザで実行されます。
4. **管理者を狙える経路**: 管理画面 `static/admin.html:701` の `openToggleDialog(${u.id},'${esc(u.username)}',...)`。ユーザー名には文字種の制限がない（丙-3）ため、攻撃者が `'` を含むユーザー名で登録し、管理者がそのユーザーの「停止」ボタンを押すと、管理者のブラウザで攻撃者の JS が動きます。同ファイル `:728` の削除ボタンも、作者の作品タイトルで同じことが起きます。
5. **自分だけに効く経路（影響は軽いが実在）**: 作者画面でファイル名を無加工で `innerHTML` に入れる箇所が3つあります（サムネイル名 `static/index.html:721`、エラー表示 `:780`、表紙プレビュー `:814`）。これは自分のファイル名で自分の画面を壊す自己 XSS なので深刻度は低いですが、少なくとも表示崩れは起きます。モチーフチップ生成（`:983-986`）も自分の入力に対して無加工です。
- 修正案: ①値の埋め込みは `textContent` と `addEventListener`（データは `dataset` 経由）に置き換え、`innerHTML` への文字列組み立てをやめる。②サーバー側で `genre_tags` を固定表と突き合わせて保存する（表に無い値は捨てる）。③ユーザー名に使える文字を英数字と一部記号に制限する（丙-3 と同時に対処）。④どうしても属性に埋める場合は JS 文字列専用のエスケープを別に用意する。

### N-3リアクション機能がビューワー側で4重に断絶している

- 場所: `yomima/templates/reader.html` と `yomima/main.py` の `reader()`、対する本物は外側 `main.py:1146` と `:1165`
- 何が起きるか（4つの断絶が重なっています。どれか1つ直しても動きません）:
1. 呼出先が違う: 画面は `fetch('/reaction')`（reader.html:712）と `fetch('/reaction_counts/{id}')`（:731）を**ビューワー自身**へ送りますが、ビューワーにそのルートは無く、実測でも **404** でした（R-24）。本物はプラットフォーム側の `POST /api/public/reaction` と `GET /api/public/reactions/{public_id}`（`reactions` が複数形）です。
2. 作品IDが渡っていない: 画面は `{{ episode_public_id}}`（reader.html:36）を使いますが、`reader()` のテンプレート引数に `episode_public_id` が**そもそも入っていません**。実測で描画結果は空文字でした。空のため `IS_PLATFORM` が常に偽になり、`sendReaction()` は先頭で何もせず戻ります。
3. 件数を読みに行く処理が呼ばれていない: `loadReactionCounts()`（reader.html:728）は定義だけで、起動処理 `boot()` からも他の場所からも呼ばれていません。
4. バーを出す処理が無い: `#reaction-bar` は `hidden` のままで、外すコードが画面のどこにもありません（最終ページ到達時の表示処理が存在しない）。
- しかも土台側にも問題があります。外側の `post_reaction` は「同じ人が押したら取り消す」作りになっておらず、画面側は `data.added` でボタンの見た目を反転させる前提なので、直通させても表示と DB がずれます（乙-2 と合わせて直す対象）。
- 修正案: ビューワーに中継ルート（例 `POST /reaction`、`GET /reaction_counts/{id}`）を作ってプラットフォームAPIへ転送するか、画面からプラットフォームへ直接送る形に統一する。あわせて `reader()` で CBZ URL から `public_id` を抜いて渡し、最終ページでバーを表示し、起動時に件数を読む。

- 何が起きるか: セッショントークンを持っていれば別のIPからでも使えます（検証はトークンの有無だけ）。その場合、スクランブルBの種は発行者のIP由来なのに、RFVP/QR に埋まるのはリクエスト者のIP、という混ざった記録になります。意図した設計（例: 共有リンク前提）なのか、発行者と利用者を同一視する前提が崩れたときの事故なのかが、コードからは読み取れませんでした。本件は断定せず、**設計判断の確認事項**として置きます。
- 直す場合の案: 検証時に発行時IPと突き合わせる（ただしプロキシ環境では誤判定に注意）、または透かしに使うIPをセッション側に統一する。

## 第6部 要確認（根拠はあるが断定しないもの）

- **Y-1 URL ファイルの受け渡しの食い違い**: ビューワーの `get_viewer_base_url()`（`yomima/main.py:49-61`）は「自分のURL」を `platform_url.txt` という名前のファイルから読みます。Cloudflared 経路ではビューワー側 setup がその名前で自分のURLを書くので合いますが、**Bore 経路ではそのファイルを書かない**ため、既定の localhost に落ち、プラットフォーム側の Referer 検査（丙-6）と食い違って CBZ が取れない組み合わせが起こり得ます。逆にプラットフォームのURL自体は、ビューワー側では環境変数 `PLATFORM_BASE_URL`（`yomima/main.py:45`）でしか決まらず、setup が書くファイルを読みに行く作りになっていません（同一マシン運用では localhost で動いてしまうため、表面化しにくい）。実地のトンネル組み合わせでは未検証なので要確認とします。
- **Y-2 カタログとの URL 完全一致**: `reader()` は作品の特定を「カタログの `cbz_url` と文字列が完全一致するか」で行います（`yomima/main.py:287`）。プラットフォームにブラウザから見た住所と、ビューワーから見た住所（トンネルの有無など）がずれると一致せず、スクランブル設定やタイトルが取れずに既定値へ落ちます。N-4 のプレビューの問題と同根で、起こるかどうかは運用形態によります。
- **Y-3 CBZ トークン検証の例外**: `exp` を欠いたトークン（正しい署名付き）で `_verify_cbz_token` が `KeyError` を投げました（R-9）。署名鍵を知らない外の人はこの形を作れないため実害はほぼありませんが、「検証に失敗したら False」が関数の約束なので、例外で 500 になる前に直しておくのが安全です（`yomima` 側ではなく外側 `main.py:141`）。
